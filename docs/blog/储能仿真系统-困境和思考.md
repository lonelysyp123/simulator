# 储能仿真系统-困境和思考

> 本文基于 **EssSimulator**（`.NET 8` 储能端到端仿真与 Modbus 联调程序）的工程实践，从「为什么需要仿真」与「仿真本身难在哪里」两个角度做归纳，供同类项目复盘与对外沟通使用。

---

## 1. 联调与验证阶段的现实困境

### 1.1 真机与现场成本

储能系统涉及电池舱、PCS、变压器、断路器、并网电表以及 EMS/调度等多角色协同。若在**尚未完成策略与接口闭环**的阶段就依赖真机：

- **时间窗口受限**：设备排产、到货、上电、并网手续往往拉长迭代周期。
- **安全风险**：功率、并网条件、保护策略未充分验证时，现场试错代价高。
- **场景不可复现**：电网波动、负载突变、故障注入在真机上难以稳定、可重复地复现。

因此，团队需要一种能在办公桌面上**长期运行、可脚本化、可版本化**的替身，让上位机、EMS、通讯网关先与「行为足够像真的」对象握手。

### 1.2 「只 mock 接口」往往不够

仅返回静态寄存器值的假从站，能快速打通**读路径**，但难以支撑：

- **功率—电压—电流**在变压器、负载模型下的耦合；
- PCS **爬坡、限幅、故障**与电池侧 **SOC、直流电压/电流** 的联动；
- 断路器分合闸后**拓扑与并网可用性**变化。

若仿真过于简陋，联调阶段发现的 bug 会在上真机后集中爆发，反而拖慢整体节奏。

### 1.3 协议与点表的双重负担

工业侧常见 **Modbus TCP** 点表（地址、功能码、缩放、语义）与研发侧**对象模型**（BMS 簇、PCS 列表、电表聚合量）并不天然一致：

- 同一名称在不同厂商 CSV 中可能含义不同；
- **缩放（Scale）** 与客户端解析约定不一致会导致「数值看起来对、物理意义错」；
- 设备数量扩展时，若点表未同步补齐（例如多路 PCS/EMU 映射），会出现**端口已开、部分通道无数据**的隐性缺陷。

这类问题不属算法难题，却极耗联调人力，需要在工具链与文档上持续投入。

## 2. 工程实现层面的思考

### 2.1 并发与实时感

仿真主循环、Modbus 多 worker、PCS 爬坡线程、外部写入控制线程同时存在时：

- 必须明确**哪些状态受同一把锁保护**、哪些路径允许异步刷新；
- 既要避免 busy-wait 占满 CPU，又要让外部客户端感受到**足够平滑的寄存器变化**。

这是典型的「不是写不出功能，而是要在稳定性与资源占用之间反复权衡」。

### 2.2 控制职责边界：谁说了算？

以无功为例：若 PCS 在本地自动改写无功目标，外部 EMS 通过 Modbus 下发的设定可能被覆盖，联调时会产生「我写了寄存器，为什么行为不符合预期」的争议。

本仓库当前取向是 **EMS 主控**：PCS 执行外部给定的有功/无功，网络与变压器等模型体现**无功对电压的反馈**。这样职责清晰，更适合验证**调度策略下的系统响应**，而不是把 PCS 自主策略再仿真一遍（后者应单独建模与开关）。

### 2.3 仓库与工具链的「小摩擦」

例如根目录存在多个解决方案/项目文件时，开发者在目录下直接执行 `dotnet build` 可能触发 CLI 无法判定目标的错误——这类问题与领域无关，却会反复绊倒新人。

**启示**：除了写清文档，还应在 README/手册中把「推荐的一条命令」写死，降低协作成本。

---

## 3. 小结：困境不是「要不要仿真」，而是「仿真到什么程度」

- **困境**来自：真机贵、场景难复现、协议与对象模型割裂、多线程与职责边界复杂。
- **思考**应落在：仿真粒度与联调目标对齐、点表与拓扑可维护、控制边界与文档一致、把易错操作固化成可复制的命令与检查清单。
